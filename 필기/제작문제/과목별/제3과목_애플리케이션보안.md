# 🛡️ [필기 자작문제] 제3과목: 애플리케이션 보안 (2026 최신 트렌드 대비)

> **출제 기준:** 생성형 AI 및 LLM 보안(OWASP Top 10 for LLM), 소프트웨어 공급망 보안(SBOM), 최신 API 보안  
> **문항 형식:** 4지 선다형 (기출 5대 Trap 구조 완벽 적용)

### [문항 1] OWASP Top 10 for LLM 및 생성형 AI 보안 (난이도: 상)
**Q1. 최근 생성형 AI 도입 확산에 따라 OWASP에서 발표한 '대규모 언어 모델(LLM) 애플리케이션 10대 보안 취약점'에 대한 설명으로 가장 옳지 않은 것은?**

① `프롬프트 인젝션(Prompt Injection)`은 공격자가 입력값을 조작하여 LLM의 내부 시스템 프롬프트(안전 지침)를 우회하거나 모델의 의도된 동작을 강제로 변경하는 공격이다.  
② `간접 프롬프트 인젝션(Indirect Prompt Injection)`은 외부 웹페이지나 PDF 파일 등에 악의적인 지시문을 숨겨두고, LLM이 인터넷 검색이나 문서 요약 시 이를 읽어 실행하도록 유도하는 공격이다.  
❸ `안전하지 않은 출력 처리(Insecure Output Handling)`는 사용자가 입력한 프롬프트의 유해성만을 사전에 검증하면 완벽히 방어할 수 있으며, LLM이 생성한 응답 텍스트는 백엔드 시스템이나 웹 브라우저로 직접 전달해도 안전하다.  
④ `학습 데이터 오염(Training Data Poisoning)`은 모델의 사전 학습 또는 미세 조정(Fine-Tuning) 단계에서 조작된 데이터나 편향된 정보를 주입하여 백도어를 심거나 모델의 무결성을 훼손하는 공격이다.

> **[정답 및 해설]**  
> * **정답:** **❸**  
> * **해설 (Trap 분석 - 입력 검증 만능주의 왜곡 Trap):**  
>   `안전하지 않은 출력 처리(Insecure Output Handling, LLM02)`는 LLM이 생성한 출력물을 검증이나 인코딩 없이 백엔드 시스템(SQL 쿼리, 시스템 명령어)이나 사용자의 웹 브라우저(HTML 렌더링)로 직접 전달할 때 발생합니다. 공격자가 프롬프트 인젝션을 통해 LLM으로 하여금 악성 스크립트(`<script>`)나 SQL 인젝션 구문을 생성하도록 유도할 수 있으므로, **입력값뿐만 아니라 LLM의 출력값에 대해서도 반드시 HTML Entity 인코딩, 파라미터화된 쿼리, 엄격한 출력 필터링을 적용**해야 합니다.

### [문항 2] 소프트웨어 공급망 보안 및 SBOM (난이도: 중상)
**Q2. 오픈소스 라이브러리 오염 및 소프트웨어 공급망(Software Supply Chain) 공격에 대응하기 위한 기술에 대한 설명으로 가장 옳은 것은?**

❶ `SBOM(Software Bill of Materials, 소프트웨어 자재명세서)`은 소프트웨어를 구성하는 모든 오픈소스 컴포넌트, 버전 정보, 라이선스, 의존성 관계를 표준화된 기계 판독형 형식으로 나열한 명세서이다.  
② SBOM의 대표적인 국제 표준 형식으로는 SPDX와 CycloneDX가 있으며, 두 형식 모두 바이너리 실행 파일의 소스코드를 완전히 역컴파일하여 복원하는 기능을 필수 요구사항으로 규정한다.  
③ 오픈소스 컴포넌트의 알려진 보안 취약점(CVE)을 조기에 식별하는 SCA(Software Composition Analysis) 도구는 정적 소스코드 보안 진단 도구(SAST)와 동일한 메커니즘으로 동작하므로 별도로 도입할 필요가 없다.  
④ 패키지 매니저(npm, PyPI 등)에서 유명 오픈소스 패키지의 오타를 이용해 악성코드를 배포하는 공격 기법을 '워터링 홀(Watering Hole)' 공격이라고 한다.

> **[정답 및 해설]**  
> * **정답:** **❶**  
> * **해설 (핵심 출제 포인트):**  
>   * ① 미국 백악관 행정명령 14028 및 과기정통부 소프트웨어 공급망 보안 가이드라인에 따라 SBOM은 소프트웨어 투명성 확보와 취약 컴포넌트 신속 조치의 필수 표준입니다. (옳음)
>   * ② SPDX(Linux Foundation)와 CycloneDX(OWASP)는 컴포넌트 메타데이터, 버전, 해시값, 의존성 관계를 표현하는 명세서이며, 소스코드 역컴파일 복원 기능과는 무관합니다. (오답)
>   * ③ SAST(정적 분석)는 개발자가 직접 작성한 소스코드의 시큐어 코딩 규칙 위반을 검사하는 반면, SCA(소프트웨어 구성 분석)는 외부 오픈소스 라이브러리의 버전과 CVE 데이터베이스를 대조하여 취약점을 찾는 별개의 기술입니다. (오답)
>   * ④ 유명 패키지의 철자 오타를 노려 악성 라이브러리를 등록하는 기법은 **'타이포스쿼팅(Typosquatting)'** 공격입니다. 워터링 홀은 표적 집단이 자주 방문하는 웹사이트를 감염시키는 표적형 공격입니다. (오답)

### [문항 3] OWASP API Security Top 10 - BOLA 취약점 (난이도: 상)
**Q3. 마이크로서비스(MSA) 및 클라우드 환경에서 가장 치명적인 취약점으로 꼽히는 OWASP API Security Top 10의 'BOLA(Broken Object Level Authorization)'에 대한 설명으로 가장 옳지 않은 것은?**

① 전통적인 웹 취약점 분류인 IDOR(Insecure Direct Object Reference, 안전하지 않은 직접 객체 참조)가 API 환경에 특화된 형태이다.  
② 엔드포인트 URL이나 요청 파라미터에 포함된 객체 식별자(ID)를 공격자가 다른 사용자의 ID(예: `/api/v1/users/1001` $\rightarrow$ `/api/v1/users/1002`)로 변조하여 타인의 데이터를 열람하거나 조작하는 취약점이다.  
❸ 사용자가 유효한 로그인 토큰(JWT 등)을 보유하고 서버가 이를 정상 검증하였다면, BOLA 취약점은 아키텍처 구조상 원천적으로 발생할 수 없다.  
④ BOLA를 방어하기 위해서는 단순히 사용자의 인증(Authentication) 여부만 확인할 것이 아니라, 요청한 사용자가 해당 특정 객체(레코드)에 접근할 정당한 인가(Authorization) 권한이 있는지를 데이터베이스 계층에서 매 요청마다 엄격히 검증해야 한다.

> **[정답 및 해설]**  
> * **정답:** **❸**  
> * **해설 (Trap 분석 - 인증과 인가의 개념 혼동 Trap):**  
>   BOLA 취약점의 핵심 원인은 **"유효하게 인증된(Authenticated) 사용자가 자신에게 권한이 없는(Unauthorized) 다른 사용자의 객체에 접근"**할 수 있는 인가 통제의 결함입니다. 즉, 사용자가 정상적인 JWT 토큰을 발급받아 로그인에 성공했더라도, 서버가 `현재 로그인한 사용자 ID == 조회하려는 레코드의 소유자 ID`인지 대조하지 않는다면 BOLA 취약점이 발생합니다. 따라서 유효한 토큰 검증만으로는 BOLA를 막을 수 없습니다.
